**Training methods and data plan for Tiny Aya — research checked 2026-11-05**

Status: proposal awaiting user agreement and independent Claude review. No paid jobs, dataset downloads, training-data generation, training, or publication were performed for this review. The user's new planning envelope is $30–50 for experimentation, subject to agreeing on the methods and runs first. This replaces the earlier assumption that the research must fit the remaining approximately $18 in credits.

**For the reviewer.** Start with [HANDOFF.md](../HANDOFF.md), including its Claude review brief, and the completed experiment reports it lists. Independently check the linked papers, data releases and implementation assumptions. The method ranking is a recommendation, the experiment sizes and budget allocations are provisional, and no improvement from GRPO or SDPO has been measured in this project. Report corrections and recommend a smaller or different study where warranted. The original sealed test stays closed.

**Recommendation.** Keep a diverse SFT checkpoint as the common starting point, then branch into verified self-training, multi-turn execution-reward GRPO, and, if its integration and teacher-quality checks pass, feedback-based self-distillation. Compare the branches on the same unseen databases and inference budget. SFT is the control and initialization; the research question is whether learning from the student's own interactions improves generalization and repair. Treat the current eight-family adapter as a reference checkpoint.

The existing trajectories are carefully checked but cover a narrow distribution. An algorithm comparison on those saturated eight families would have little room to distinguish methods. Give every branch the same richer task pool and evaluator so a data change cannot be mistaken for an optimizer improvement.

Verified self-training is often called rejection-sampling fine-tuning, or RFT. It samples several student attempts, keeps execution-verified successes, and fits them with a supervised loss. It changes the training distribution but remains an SFT optimization objective. Do not present it as the sole experiment beyond SFT. Also distinguish this meaning of RFT from papers using the same abbreviation for reinforcement fine-tuning.

RLOO is available as a fallback in our installed AgentTune. Sweeping RLOO, GRPO, GSPO, CISPO and several GRPO loss variants would consume the budget without answering a focused question. Choose one supported RL objective, then investigate the training signal and measured behavior.

**Proposed comparison.** The counts below are planning targets. A preregistration should freeze the actual selection and budgets after an approved throughput preflight.

- Use approximately 1,000–2,000 executable training tasks across many databases, sampled for query-structure diversity and feasible context/query size. Include a fixed portion of existing training trajectories to preserve protocol behavior. Use SynSQL initially, with a checked SQaLe 2 slice if materialization and schema sizes fit.
- Separate training, development and final evaluation by database/schema identity. Hold related phrasings and normalized duplicate queries together. Check cross-source overlap. Use roughly 100–150 development tasks and 150–200 final tasks, with an external BIRD slice. Report any subset and exclusions before looking at model outcomes.
- Include untuned zero-shot, a fixed few-shot prompt baseline and the existing pilot on a bounded development slice. Freeze the examples and output protocol. This checks whether training adds useful capability beyond teaching the tool format through prompt examples. Budget these screens before expanding evaluation to the selected final candidates.
- A: diverse SFT control, starting from the same Tiny Aya base and using the established assistant-only mask.
- A-continued: extra SFT on the original approved mixture, with a continuation budget matched to the relevant post-training comparison. This checks whether extra training alone explains a gain.
- B: A plus one verified self-training round. Reuse training-only sampled trajectories, keeping successes and controlling duplicate/easy-task domination.
- C: A plus multi-turn GRPO on the same training-question pool. Begin with correctness-dominated reward and real database feedback. Use a bounded difficulty curriculum and log groups with zero reward variation. Keep partial execution rewards a declared ablation; an executable wrong query is still wrong.
- D, stretch: A plus SDPO-style feedback self-distillation. The self-teacher sees real feedback and, when available, a verified successful training rollout. The evaluated policy sees only the ordinary task/tools. If reference SQL is introduced as privileged teacher context, declare that as a separate supervised-information condition.

B, C and D branch from A. Running them sequentially would confound the comparison. Use the same tools, tokenizer, quantization, task pool, inference limits and checkpoint-selection rule. Match rollout budgets where possible and report actual generated tokens, update tokens, teacher passes, wall time and cost; equal optimizer steps do not imply equal compute.

**A verifier upgrade is a prerequisite for RL.** The current `src/ayadb/metrics.py` requires the correct scalar answer plus any successful query. That is useful for our existing tasks but is too weak as the only reward for a broad SQL study.

- Identify an explicitly submitted final SQL query, and verify its full result against the reference execution. Preserve row multiplicity, apply ordering rules when relevant, and preregister numerical tolerances.
- Tie the submitted result to the actual executed query. A successful unrelated query must not ground the final answer.
- Agent-visible row limits may stay small, but scoring must not compare only two matching truncated previews. Bound verifier runtime and result size with an explicit overflow policy.
- Keep reference SQL, reference outputs and oracle diagnostics out of evaluation observations. An ordinary execution tool can report runtime errors; it cannot know that a valid query answers the wrong question.
- On supported synthetic tasks, add a counterexample diagnostic using several constraint-preserving database instances. Treat passing these checks as stronger evidence, not a proof of general semantic equivalence. Preserve the benchmark's standard execution metric separately.
- Evaluate repair both end to end and from fixed failed-query prefixes whose errors were obtained by actually executing those queries. Score eventual correct results after the error; report this continuation stress test separately from natural error frequency. Column renaming alone does not guarantee a recovery test.

**Implementation feasibility checked in this workspace.** Installed versions are AgentTune 1.1.3, TRL 1.7.1, transformers 5.22.1 and PEFT 0.21.2. No training was run during inspection.

AgentTune's installed factory exposes GRPO and RLOO but not SDPO. Its GRPO wrapper intercepts generation for its custom multi-turn rollout, including observation masking. This provides a plausible integration route, not evidence that Tiny Aya RL already works. The installed TRL includes an experimental SDPO trainer with sampled-token/top-k modes and LoRA teacher handling. Its generation path is separate from AgentTune's GRPO wrapper; a complete tool rollout and mask integration still needs engineering. Native availability does not make it a one-line switch.

Keep `official_tokenizer`, explicit assistant/tool masks and actual tool feedback. Verify generated token log-probabilities, the tool-observation mask, finite gradients, adapter updates and independently reloaded checkpoints before long runs. Tiny Aya's large vocabulary makes memory profiling important, especially for full-logit self-distillation. Start with a sampled-token implementation if supported. Do not change quantization only for one experimental arm without reporting that confound.

Two corrections to the earlier research memo: equal-reward GRPO groups have no outcome-advantage signal, but curricula or additional rewards can change that; this is not a universal impossibility result for small models. Also, the installed `DecideAuditReader.extract_dpo_pairs` does read human-feedback records, so the old assertion that it always returns an empty list is stale. Those records are not automatically usable SQL trajectory preferences.

**Decision gates and side effects.**

1. After agreement, preregister the data eligibility rules, splits, arms, primary metric, budgets and stop rules. Use one approved run per preregistration. The spent `data/test.jsonl` remains closed.
2. First measure sampled success/variation on training-only tasks. If binary rewards are uniformly zero, improve the common starting policy or choose a feasible curriculum before committing to a long binary-reward GRPO run. If a constrained run never gains an informative signal, label it a feasibility failure rather than a definitive test of RL's potential.
3. Before D, check whether conditioning Tiny Aya on real feedback or a successful training attempt produces a useful teacher. Cap integration work; if masks, memory or teacher quality fail the predeclared checks, keep the result and use the remaining budget on the supported comparison.
4. Select configurations only on the new development set. Predeclare a practically useful target, such as a 10 percentage point correctness gain or comparable correctness with 20% lower inference cost. Report paired gains/losses and uncertainty, with database-level grouping where tasks are correlated. A single training seed remains a limitation.
5. Run a final frozen evaluation of selected models once. Report execution accuracy, genuine recovery, schema/phrasing robustness, malformed/fabricated behavior, loops and cost per success. Preserve a standard benchmark score alongside stricter diagnostics.
6. Check retention on the existing 40-task dev set for the final candidate and its control. If time and the stretch allocation remain, evaluate a fixed sample from [When2Call](https://huggingface.co/datasets/nvidia/When2Call) (CC BY 4.0) and a small instruction-following set. These are targeted regression checks; broad safety, multilingual and general-intelligence claims would need a larger study. Skip a broad benchmark suite if it would prevent completing the main experiment.

The intended contribution is a controlled, budgeted study of whether interaction-based training makes Tiny Aya a better database agent on unfamiliar schemas, with a demonstrable repair behavior and an honest accounting of failures and retained capabilities. Method choice is driven by this question, not by a requirement that the newest algorithm win.
